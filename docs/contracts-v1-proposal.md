# ACID Contracts v1 — Proposal

> **Status: Draft / Under Review**
>
> This document proposes the initial JSON contracts for ACID Event,
> Detection, and Incident objects. These definitions are not finalized
> until reviewed and approved by the Backend team.

## 1. General conventions

- JSON format.
- Field names use `snake_case`.
- Timestamps use ISO 8601 UTC.
- Contract version: `v1`.
- Required fields must not be missing or null.
- Optional fields may be omitted or null where explicitly allowed.

---

## 2. Event

An Event represents an observed activity collected from a monitored
system or security data source.

### Proposed fields

| Field | Type | Required | Description |
|---|---|---|---|
| `event_id` | string | Yes | Unique event identifier |
| `timestamp` | string | Yes | UTC event timestamp |
| `event_type` | string | Yes | Event classification |
| `source` | string | Yes | Origin of the event |
| `src_ip` | string/null | No | Source IP address |
| `dst_ip` | string/null | No | Destination IP address |
| `src_port` | integer/null | No | Source port (0–65535) |
| `dst_port` | integer/null | No | Destination port (0–65535) |
| `protocol` | string/null | No | Network protocol |
| `raw_data` | object/null | No | Original event data |

### Example

\`\`\`json
{
  "event_id": "evt-001",
  "timestamp": "2026-11-24T10:30:00Z",
  "event_type": "network_connection",
  "source": "firewall",
  "src_ip": "192.168.1.10",
  "dst_ip": "192.168.1.20",
  "src_port": 52344,
  "dst_port": 22,
  "protocol": "tcp",
  "raw_data": {}
}
\`\`\`

## 3. Detection

A Detection represents a security finding generated by a rule,
analytics component, or detection engine.

### Proposed fields

| Field | Type | Required | Description |
|---|---|---|---|
| `detection_id` | string | Yes | Unique detection identifier |
| `event_id` | string | Yes | Related event identifier |
| `detection_type` | string | Yes | Detection classification |
| `severity` | string | Yes | Severity level |
| `confidence` | number | Yes | Confidence score from 0.0 to 1.0 |
| `description` | string | Yes | Detection explanation |
| `timestamp` | string | Yes | UTC detection timestamp |
| `technique` | string/null | No | Primary MITRE ATT&CK technique |
| `techniques` | array[string] | No | Associated ATT&CK techniques |

### Proposed severity values

- `low`
- `medium`
- `high`
- `critical`

### SSH detection requirements

The contract must support:

- `detection_type = "ssh_bruteforce"`
- `technique = "T1110.001"`
- `techniques = ["T1046", "T1110.001"]`

MITRE technique identifiers must be validated against an approved
ATT&CK technique catalog, not only a string-format regular expression.

### Example

\`\`\`json
{
  "detection_id": "det-001",
  "event_id": "evt-001",
  "detection_type": "ssh_bruteforce",
  "severity": "high",
  "confidence": 0.95,
  "description": "Multiple failed SSH authentication attempts detected",
  "timestamp": "2026-11-24T10:35:00Z",
  "technique": "T1110.001",
  "techniques": ["T1110.001"]
}
\`\`\`

## 4. Incident

An Incident represents a grouped security case containing one or more
related detections.

### Proposed fields

| Field | Type | Required | Description |
|---|---|---|---|
| `incident_id` | string | Yes | Unique incident identifier |
| `title` | string | Yes | Incident title |
| `status` | string | Yes | Incident lifecycle status |
| `severity` | string | Yes | Incident severity |
| `detection_ids` | array[string] | Yes | Related detection IDs |
| `created_at` | string | Yes | UTC creation timestamp |
| `updated_at` | string | Yes | UTC update timestamp |
| `description` | string/null | No | Incident details |

### Proposed status values

- `open`
- `investigating`
- `contained`
- `resolved`
- `closed`

### Example

\`\`\`json
{
  "incident_id": "inc-001",
  "title": "SSH Brute Force Activity",
  "status": "open",
  "severity": "high",
  "detection_ids": ["det-001"],
  "created_at": "2026-11-24T10:35:00Z",
  "updated_at": "2026-11-24T10:35:00Z",
  "description": "Repeated SSH authentication failures targeting a host"
}
\`\`\`

## 5. Contract testing scope

Contract tests should validate:

1. Valid Event payloads are accepted.
2. Valid Detection payloads are accepted.
3. Valid Incident payloads are accepted.
4. Missing required fields are rejected.
5. Invalid field types are rejected.
6. Invalid IP addresses are rejected when an IP is supplied.
7. Ports outside the range 0–65535 are rejected.
8. Confidence values outside 0.0–1.0 are rejected.
9. `ssh_bruteforce` is accepted as a detection type.
10. `T1110.001` is accepted as a valid ATT&CK technique.
11. `T9999` is rejected as an unknown technique.
12. Multiple techniques such as `["T1046", "T1110.001"]` are accepted.

## 6. Open decisions for Backend review

Before implementation, the Backend team must confirm:

- Exact required and optional fields.
- Identifier format (UUID or string).
- Allowed event and detection types.
- Severity and status enumerations.
- MITRE technique validation source/catalog.
- Whether `technique` and `techniques` coexist or one replaces the other.
- Timestamp field naming and format.
- Whether Event, Detection, and Incident schemas are JSON Schema,
  Pydantic, C# DTOs, or another implementation.
